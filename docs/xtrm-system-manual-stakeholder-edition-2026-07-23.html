01 · stakeholder view

The system reduces context loss without hiding authority.

Multiple agents can work concurrently, but each action remains attached to a task, runtime, branch, parent, result, and evidence trail. Automation accelerates execution; it does not erase responsibility.

01 · isolation

Every runtime has a boundary

Interactive coordinators and Specialist jobs use distinct branches and worktrees.

02 · traceability

Every job has a lineage

Pane, coordinator, Bead, job, branch, commit, and integration can be reconstructed.

03 · bounded context

Delegation protects the parent

Coordinators consume structured results and escalate only judgment and blockers.

04 · durable coordination

Messages survive transitions

xtmux persists messages, obligations, monitors, wakes, and completed turns.

05 · explicit authority

Each concept has one owner

Git owns merge truth; Beads work truth; Specialists jobs; xtmux delivery.

06 · deterministic direction

Templates replace procedural memory

The next program moves graphs, gates, and exact dispatch into versioned templates.

02 · repository system map

Three repositories, one operating model.

The repositories are deliberately incomplete in isolation. Their value comes from narrow, versioned seams rather than duplicated orchestration logic.

xtrm-dev/core

Launch and integration plane

Creates interactive runtimes and their branch/worktree boundaries.

  • xt claude / xt pi
  • runtime compatibility preflight
  • coordinator pane and branch metadata
  • aggregated topology
  • installed-asset and update contracts
⇄
xtrm-dev/specialists

Role and job plane

Owns effective roles, execution, timeline, result, worktrees, and descendant lineage.

  • sp view / sp render-task
  • sp run / sp feed / sp result
  • chain coordinator and Specialist definitions
  • runtime-origin propagation
  • integration evidence
⇄
Jaggerxtrm/xtmux

Runtime control plane

Turns tmux into typed identity, delivery, wake, monitoring, and observation.

  • pane/session topology
  • messages and reply obligations
  • monitors and one-shot wakes
  • message-get / agent-last
  • read-only bridge and journal

Connecting rule: Core never becomes a second Specialist supervisor; Specialists never becomes a second message bus; xtmux never decides task semantics or merge judgment.

05 · user perspectives

Different readers see the same truth at different depth.

stakeholderNeeds outcome confidence

Reads scope, release state, current risks, decision gates, and whether delegated work reached a verified integration outcome.

operatorOwns runtime and authority

Launches coordinators, verifies topology, handles approvals, inspects failures, and integrates coordinator branches into main.

coordinatorOwns one work scope

Claims sub-beads, dispatches Specialists, consumes results, integrates accepted branches, and escalates judgment.

maintainerOwns contracts and releases

Changes schemas, CLI boundaries, release gates, skills, adapters, and compatibility with coordinated tests.

06 · end-to-end lifecycle

From one task to a verified integration result.

The lifecycle separates launch, execution, delivery, integration, and evidence. Each transition has an owning component.

Bead contract→Core launches coordinator→template resolves node→Specialists runs job→NDJSON progress→typed parent message→result + integration→Git verification

Current vs target: structured NDJSON and result retrieval are landed. The direct typed Specialists→parent message and canonical template resolver are the next architecture program.

Acknowledgment rule: message-get is a read. Acknowledge only after the continuation has been queued successfully: message-get → queue → message-ack.

08 · practical user manual

Operate the system through repeatable procedures.

Runbook index

Commands assume a tmux-attached operator inside the target repository.

01 · preflight

Verify the installed trio

required

Do this before diagnosing cross-repository behavior. Source main and installed package behavior may differ.

xt version --json xtmux-obs version --json sp version --json node --version
02 · launch

Create a detached chain coordinator

Core

Capture the stable parent session and force a new session so the supervising pane remains active.

parent=$(tmux display-message -p '#{session_id}') xt pi release-hardening \ --role chain-coordinator \ --bead xtrm-release-hardening \ --new-session \ --no-attach \ --parent "$parent"
03 · verify

Inspect identity before delegation

Core + xtmux

Confirm branch, worktree, parent, role, Bead, and runtime identity.

xt topology --view summary xt topology --view chains xtmux topology --json xtmux context --current --json
04 · dispatch

Start bounded Specialist work

Specialists

The current transitional command is explicit. The target architecture derives these flags from a canonical chain template.

sp run explorer \ --bead xtrm-release-hardening.1 \ --worktree \ --json
05 · progress

Consume structured lifecycle events

NDJSON

Use the Pi-compatible stream for live workflow integration or replay. Per-job order is canonical by sequence.

sp feed <job-id> --json sp feed --job <job-id> --follow --json sp feed --from <job-id>:<seq> --json
06 · message

Retrieve an exact xtmux notification

notification target

The direct Specialist parent-notification contract is proposed but not yet landed. Generic messages already use this retrieval model.

xtmux message-get <message-key> --json # queue the continuation successfully xtmux message-ack <message-key> --json
07 · result

Retrieve or resume the Specialist

authoritative

Use the complete result for terminal work. Waiting work resumes through Specialists, not through terminal guessing.

sp result <job-id> --json sp resume <job-id> "Approved: use the narrower scope"
08 · integration

Merge into the coordinator branch and record evidence

Git remains truth

After a verified merge, record the observed relationship through the public Specialists CLI.

git merge --no-ff sp/executor-<job> sp integration record \ --source-branch sp/executor-<job> \ --source-worktree /repo/.xtrm/worktrees/<job> \ --source-job-id <job-id> \ --target-branch "$XTMUX_AGENT_BRANCH" \ --target-worktree "$PWD" \ --target-role chain-coordinator \ --commit "$(git rev-parse HEAD)" \ --json sp integration list --job <job-id> --json
09 · close

Account for jobs, branches, reviews, and resources

completion gate

A chain is not complete while active jobs, unresolved review threads, or unintegrated branches remain unreported.

sp ps --json xtmux obligations list --json xtmux monitors --all git status --short git branch --no-merged sp integration list --target-branch "$XTMUX_AGENT_BRANCH" --json
09 · deterministic orchestration target

Dispatch and chain templates must land as one contract.

The roadmap and the modernization PRD propose canonical templates. Exact dispatch should be produced by the same resolver, not added as an isolated launcher feature.

Selected template
Versioned nodes, roles, dependencies, scrutiny, output types, conditions, gates, retry, approval, integration, cleanup, and completion criteria.
canonical input
Single resolver
Computes the DAG, eligible nodes, exact Specialist and flags, assigned parent, result contract, and expected notification or monitor behavior.
one interpretation
Exact dispatch
The launcher consumes the plan; it does not improvise dependencies, target branch, reviewer requirements, or next-step rules.
deterministic action
Coordinator judgment
Handles semantic ambiguity, exceptions, conflicts, authorized integration, operator interaction, and escalation.
human-level reasoning
Evidence
Template ID, node, parameters, result type, branch, runtime origin, transition, and integration outcome remain reconstructable.
forensic trail

Landing dependency: Core, Specialists, xtmux, prompts, and an Archon adapter must not each implement a partial chain interpreter. The template resolver is the shared source of dispatch truth.

10 · Archon experiment

Archon is a workflow experiment, not a replacement authority.

The discussion began from the working PRD Archon + XTRM — QuestDB Maintenance Workflow Plan. Its value is the evidence it provides for declarative DAGs, typed artifacts, deterministic gates, approvals, and independent post-action verification.

first experiment

QuestDB planning workflow

  • read-only evidence gathering
  • deterministic GO / NO-GO
  • typed maintenance plan
  • no production mutation
  • compare native and Specialists-backed nodes
later only

QuestDB execution workflow

  • approved plan as input
  • fresh live preflight
  • explicit approval
  • checkpointed mutation
  • independent verification and rollback
thin Archon → Specialists adapter
Archon node
  → sp run <specialist> --bead <id> --json
  → consume ordered session / turn / message / tool events
  → observe agent_end and agent_settled
  → sp result <job-id> --json
  → return typed node output

Never: scrape panes · parse human feed · read private SQLite · create a second XTRM worktree · override deterministic NO-GO

Archon may own

Its experimental DAG, ordering, parallelism, conditions, retry, artifact passing, and approval presentation.

XTRM retains

Runtime placement, Specialist lifecycle, xtmux delivery, Beads task truth, Git integration truth, and forensic identity.

Decision after evidence

External engine, template builder/exporter, or reference-only pattern source. No production compiler before the scorecard.

13 · recommended sequence

Close the audit first; build determinism second.

Phase 1

Close P1 and security findings

Public export, immutable runner protection, xtmux Beads cursor, and complete topology source ledger.

Phase 2

Close P2 and release current source

Topology/routing/reuse/Serena/index/cache, Claude capture, integration parser/target, review threads, Specialists test baseline and patch release.

Phase 3

Land deterministic orchestration foundation

Canonical templates, one resolver, exact dispatch, direct parent notification, canonical skills, and extended live Suite C.

Phase 4

Run experiments

QuestDB Archon planning A/B, deterministic merge FIFO, and read-only worktree hygiene.

Phase 5

Make the Archon adoption decision

External engine, template builder/exporter, or reference-only pattern source—based on measured evidence.
